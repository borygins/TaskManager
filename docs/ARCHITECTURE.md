# Архитектура проекта

## Цель MVP

Приложение предназначено для менеджеров по продажам и начальника:

- общие воронки продаж;
- уникальные клиенты;
- один ответственный менеджер на клиента;
- один и тот же клиент может участвовать в нескольких воронках;
- изменения фиксируются в журнале активности за текущий день;
- импорт и экспорт через Excel;
- ежедневный локальный бэкап SQLite.

## Стек

- Python 3.13
- FastAPI
- SQLAlchemy 2.x async ORM
- SQLite в WAL-режиме
- HTML + CSS + Jinja2
- APScheduler для ежедневного бэкапа
- openpyxl для Excel

## Структура

- `app/main.py` - точки входа FastAPI и маршруты.
- `app/core/` - конфигурация и безопасность.
- `app/db/` - база и инициализация SQLAlchemy.
- `app/models/` - ORM-модели.
- `app/services/` - бизнес-логика, импорт/экспорт, сидирование, бэкапы.
- `app/templates/` - HTML-шаблоны.
- `app/static/` - CSS и JavaScript.
- `backups/` - ежедневные резервные копии базы.

## Ключевые решения

### 1. Клиент уникален

Уникальность задана по `tax_number` как по налоговому номеру. Это важно для будущего объединения воронок без дублирования карточек клиента.

### 2. Несколько воронок на одного клиента

Используется связующая таблица `client_funnels`. Поэтому одна карточка клиента может участвовать одновременно в кампаниях `Доля рынка`, `Спарк` и будущих воронках.

### 3. Один менеджер на клиента

Поле `assigned_manager_id` хранится в карточке клиента. Это гарантирует, что клиент не находится одновременно в работе у разных менеджеров.

### 4. Снижение количества записей в БД

Редактирование карточки делается через форму и одну кнопку `Сохранить изменения`. Только после сохранения изменения уходят в базу.

### 5. Контроль активности

Любое важное изменение по клиенту пишется в `activity_logs`:

- статус;
- комментарий;
- дата звонка;
- следующая дата звонка;
- назначенный менеджер;
- заметки и важные поля клиента.

## Учёт контактов и отчётность

Создание новых клиентов вынесено в `app/api/clients.py` и `app/services/clients.py`. Маршруты `/clients/new` регистрируются до `/clients/{client_id}`. Клиент, связь с воронкой и запись журнала создаются в одной транзакции. Если автор — менеджер, ответственным становится он; если руководитель — `assigned_manager_id` остаётся `NULL`. Переданный формой ответственный при создании игнорируется. В карточке руководитель может выбрать «Не назначен»: пустое значение снимает закрепление, отсутствие поля в запросе сохраняет текущее назначение. Проверка ИНН и уникальное ограничение защищают от дубликатов, включая одновременные запросы. Существующие клиенты не переназначаются и не изменяются действием создания.

- `app/api/contacts.py` — формы контактов, план, месячный журнал, дневной/месячный экспорт и повторная запись файла.
- `app/services/contacts.py` — проверка данных, запись контакта и объединение строк для обоих отчётов.
- `app/services/contact_reports.py` — оформление девятиколоночного Excel, атомарная замена файла и повторные попытки.
- `contact_activities` — отдельные звонки/встречи с автором, датой, результатом и снимками реквизитов отчёта. Существующий столбец `dialogue` сохранён для совместимости баз, заполняется автоматически по статусу и не участвует в подсчёте нормы.
- `contact_report_states` — очередь обновления дневных файлов (ключ: менеджер и день), версия последнего изменения и ошибка формирования.
- `reports/` — локальные дневные файлы, исключённые из Git. Месячная выгрузка формируется по запросу.

Новая функциональность не использует текст `activity_logs` для подсчёта контактов. Один контакт, комментарий, обновление ближайшей даты и отметка о необходимости отчёта сохраняются одной транзакцией. Старые записи не конвертируются автоматически.

Повторная отправка формы защищена подписанным идентификатором с уникальным ограничением в БД; новые POST-формы проверяют CSRF-токен сессии. Доступ к клиенту и отчёту проверяется на сервере. Историческая принадлежность контакта определяется автором, а не текущим ответственным клиента.

Группировка: `(manager_id, activity_date, client_id)`. Порядок внутри дня: время сохранения, затем ID. Последняя запись определяет поля строки и воронку; комментарии соединяются через ` = `; наличие встречи определяет вид строки. Клиент засчитывается в норму, если хотя бы одна запись группы имеет статус, отличный от `Недозвон`. Это правило применяется и к старым записям независимо от сохранённого ранее признака `dialogue`.

`Client.next_call_date` используется как ближайшая дата активности, в том числе встречи. Исторические записи за дни до последнего контакта не меняют текущий план. Результаты `Недозвон` и `Перенос на дату` не сбрасывают стадию продажи. `Договор подписан` и `Договор запущен` соответствуют стадии `Подписан`. Потенциал контакта хранится отдельно от `Client.monthly_turnover`.

После фиксации транзакции Excel формируется в рабочем потоке и записывается во временный файл рядом с целевым, затем заменяется через `os.replace`. Ошибка не отменяет контакт и не повреждает предыдущий файл. Очередь повторяется при старте и раз в минуту; расписание ежедневного бэкапа не изменено. Версия очереди предотвращает снятие отметки о более новом контакте, поступившем во время формирования. Генерация сериализована внутри процесса; приложение рассчитано на один процесс Uvicorn, как при текущем локальном запуске.

Новые таблицы создаются существующим `Base.metadata.create_all` без удаления данных. Тесты `tests/test_contacts.py` используют временную SQLite и реальные ASGI-маршруты, проверяют агрегацию, норму, права, валидацию, повторную отправку, ошибку записи и содержимое XLSX.
