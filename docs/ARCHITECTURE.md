# Архитектура проекта

## Цель MVP

Приложение предназначено для менеджеров по продажам и начальника:

- общие воронки продаж;
- уникальные клиенты;
- один ответственный менеджер на клиента;
- один и тот же клиент может участвовать в нескольких воронках;
- изменения фиксируются в журнале активности за текущий день;
- импорт и экспорт через Excel;
- ежедневный локальный бэкап SQLite.

## Стек

- Python 3.13
- FastAPI
- SQLAlchemy 2.x async ORM
- SQLite в WAL-режиме
- HTML + CSS + Jinja2
- APScheduler для ежедневного бэкапа
- openpyxl для Excel

## Структура

- `app/main.py` - точки входа FastAPI и маршруты.
- `app/core/` - конфигурация и безопасность.
- `app/db/` - база и инициализация SQLAlchemy.
- `app/models/` - ORM-модели.
- `app/services/` - бизнес-логика, импорт/экспорт, сидирование, бэкапы.
- `app/templates/` - HTML-шаблоны.
- `app/static/` - CSS и JavaScript.
- `backups/` - ежедневные резервные копии базы.

## Ключевые решения

### 1. Клиент уникален

Уникальность задана по `tax_number` как по налоговому номеру. Это важно для будущего объединения воронок без дублирования карточек клиента.

### 2. Несколько воронок на одного клиента

Используется связующая таблица `client_funnels`. Поэтому одна карточка клиента может участвовать одновременно в кампаниях `Доля рынка`, `Спарк` и будущих воронках.

### 3. Один менеджер на клиента

Поле `assigned_manager_id` хранится в карточке клиента. Это гарантирует, что клиент не находится одновременно в работе у разных менеджеров.

### 4. Снижение количества записей в БД

Редактирование карточки делается через форму и одну кнопку `Сохранить изменения`. Только после сохранения изменения уходят в базу.

### 5. Контроль активности

Любое важное изменение по клиенту пишется в `activity_logs`:

- статус;
- комментарий;
- дата звонка;
- следующая дата звонка;
- назначенный менеджер;
- заметки и важные поля клиента.

## Учёт контактов и отчётность

Общий каталог `/clients/search` реализован в `app/api/clients.py` и `app/services/clients.py`, до динамического маршрута `/clients/{client_id}`. Поиск по ИНН, ФИО и организации использует SQLite `casefold` и экранирование LIKE; фильтры — статус, воронка и ответственный. Проверка участия в воронке через `EXISTS` не дублирует клиентов. SQL-проекция выбирает только реквизиты каталога и имя ответственного, без телефонов, заметок и истории. Пагинация — по 50 клиентов. Общий каталог не расширяет права на карточки: менеджер открывает только свои, руководитель — любые.

Создание новых клиентов вынесено в `app/api/clients.py` и `app/services/clients.py`. Маршруты `/clients/new` регистрируются до `/clients/{client_id}`. Клиент, связь с воронкой и запись журнала создаются в одной транзакции. Если автор — менеджер, ответственным становится он; если руководитель — `assigned_manager_id` остаётся `NULL`. Переданный формой ответственный при создании игнорируется. В карточке руководитель может выбрать «Не назначен»: пустое значение снимает закрепление, отсутствие поля в запросе сохраняет текущее назначение. Проверка ИНН и уникальное ограничение защищают от дубликатов, включая одновременные запросы. Существующие клиенты не переназначаются и не изменяются действием создания.

- `app/api/contacts.py` — формы контактов, план, месячный журнал, дневной/месячный экспорт и повторная запись файла.
- `app/services/contacts.py` — проверка данных, запись контакта и объединение строк для обоих отчётов.
- `app/services/contact_reports.py` — оформление девятиколоночного Excel, атомарная замена файла и повторные попытки.
- `contact_activities` — отдельные звонки/встречи с автором, датой, снимком статуса, отметками и реквизитами отчёта. Старые столбцы `result` и `dialogue` сохранены для совместимости базы, заполняются автоматически и не являются полями формы.
- `contact_report_states` — очередь обновления дневных файлов (ключ: менеджер и день), версия последнего изменения и ошибка формирования.
- `reports/` — локальные дневные файлы, исключённые из Git. Месячная выгрузка формируется по запросу.

Новая функциональность не использует текст `activity_logs` для подсчёта контактов. Один контакт, комментарий, обновление ближайшей даты и отметка о необходимости отчёта сохраняются одной транзакцией. Старые записи не конвертируются автоматически.

Повторная отправка формы защищена подписанным идентификатором с уникальным ограничением в БД; новые POST-формы проверяют CSRF-токен сессии. Доступ к клиенту и отчёту проверяется на сервере. Историческая принадлежность контакта определяется автором, а не текущим ответственным клиента.

Группировка: `(manager_id, activity_date, client_id)`. Порядок внутри дня: время сохранения, затем ID. Последняя запись определяет поля строки и канал; отметки добавляются перед комментарием, комментарии соединяются через ` = `; наличие встречи определяет вид строки. При записи контакта канал определяется без поля формы: первая связь `ClientFunnel` по ID (то есть первая добавленная клиенту воронка), при отсутствии связей — снимок `Прочее` с `funnel_id = NULL`. Изменение состава или названия воронок не переписывает старый снимок. Клиент засчитывается в норму, если хотя бы одна запись группы не имеет отметки `missed_call`; старый признак `dialogue` не участвует в подсчёте.

`Client.next_call_date` используется как ближайшая дата активности, в том числе встречи. Исторические записи за дни до последнего контакта не меняют текущий план или статус. Единый каталог статусов и отметок находится в `app/core/sales.py`. Форма активности записывает `ContactActivity.client_status` и `marks` напрямую; `#недозвон` требует следующую дату, запрещён для встречи и не учитывается в норме. Потенциал для исторического снимка копируется из `Client.monthly_turnover`. Финальные статусы из `FINAL_CLIENT_STATUSES` исключаются из рабочих планов, но клиент остаётся доступен в поиске и может быть возвращён в работу следующей активностью.

После фиксации транзакции Excel формируется в рабочем потоке и записывается во временный файл рядом с целевым, затем заменяется через `os.replace`. Ошибка не отменяет контакт и не повреждает предыдущий файл. Очередь повторяется при старте и раз в минуту; расписание ежедневного бэкапа не изменено. Версия очереди предотвращает снятие отметки о более новом контакте, поступившем во время формирования. Генерация сериализована внутри процесса; приложение рассчитано на один процесс Uvicorn, как при текущем локальном запуске.

Новые таблицы создаются существующим `Base.metadata.create_all` без удаления данных. Тесты `tests/test_contacts.py` используют временную SQLite и реальные ASGI-маршруты, проверяют агрегацию, норму, права, валидацию, повторную отправку, ошибку записи и содержимое XLSX.

## Единая история комментариев

Канонический текст находится в `comments.body`. `Comment.source` различает `card`, `contact`, `import`, `legacy` (источник старой записи неизвестен) и `legacy_notes` (перенос старой заметки). Автор может быть `NULL` только для данных, чей автор неизвестен. `ContactActivity.comment_id` — обязательная уникальная ссылка на комментарий; отдельной текстовой колонки контакта больше нет. `Client.manager_notes` удалён.

Карточка и форма активности используют один шаблон `_client_history.html` и историю всех авторов по клиенту, упорядоченную по времени создания и ID. Доступ проверяется по клиенту. Журналы и норма по-прежнему выбирают контакты по их историческому менеджеру; текст читается через `comment_record`. Общая выгрузка и список воронки используют последний комментарий. `activity_logs` и планы импорта являются историческими снимками, а не дополнительными редактируемыми источниками комментариев.

Миграция `scripts/migrate_comments.py` выполняется отдельно, без импорта приложения: обязательный бэкап через Backup API, транзакционная перестройка таблиц, сохранение данных и проверка связей. `init_db` отказывается запускаться на старой схеме, а не преобразует данные автоматически. Правила сопоставления, ограничения и откат описаны в [COMMENTS_MIGRATION.md](COMMENTS_MIGRATION.md). Новая пустая база создаётся сразу с новой моделью. Интерфейс редактирования комментариев и история правок в это изменение не входят.

После неё существующая база требует офлайн-миграцию `scripts/migrate_statuses.py`: она нормализует статусы, добавляет снимок статуса и отметки активности, делает обязательный бэкап и отклоняет неизвестные значения вместо предположительного преобразования. Порядок запуска описан в [STATUS_MIGRATION.md](STATUS_MIGRATION.md).

## Единый импорт клиентов

- `app/api/imports.py` — маршруты загрузки, просмотра плана, подтверждения, отмены и скачивания общего отчёта. `/import/{batch_id}/report` возвращает все строки; прежний `/errors` оставлен как совместимый адрес этого же отчёта. Старый POST `/import`, сразу изменявший клиентов, заменён предварительной проверкой. `/import/template` регистрируется раньше динамического маршрута.
- `app/services/client_import.py` — ограниченное чтение XLSX, валидация строк, сравнение по ИНН, подготовка плана различий и его применение. Парсинг/создание XLSX выполняется вне основного цикла обработки запросов. Текст в отчёте импорта и общей выгрузке не превращается в формулы Excel.
- `client_imports` — новая таблица, добавляемая `create_all`: автор, имя файла, сериализованные исходные строки и план, состояние `pending/applied/cancelled/stale`, время создания/применения. Данные не лежат в публичной static-папке или cookie; автоматического удаления истории пока нет.
- Перед подтверждением в отдельной сессии выполняется SQLite `BEGIN IMMEDIATE`. План пересчитывается и сравнивается с сохранённым, включая снимки реквизитов, комментариев, воронок и целевого менеджера. Изменение данных либо возраст свыше 24 часов переводит загрузку в `stale` без записи клиентов. Корректные строки и отметка `applied` фиксируются одной транзакцией. Повторное подтверждение/конкурентный запрос не повторяет операцию; системная ошибка откатывает весь пакет.
- Пустые ячейки не очищают значения. У существующих клиентов заполненные ФИО, организация, телефон, дата звонка, следующая дата звонка и статус защищены от замены; пустые поля заполняются. ИНН — неизменяемый ключ сопоставления. Оборот, MCC, банк-конкурент и адрес регистрации обновляются из непустых значений. Непустой табельный номер задаёт действующего менеджера, непустой набор воронок заменяет старые связи; новые воронки создаются при применении. Комментарии добавляются в `comments`, сравниваются с существующим текстом после нормализации пробелов. `manager_notes` перенесён и удалён отдельной миграцией; новые комментарии импорта имеют источник `import`. Контакты и очередь дневных отчётов не создаются. `last_manager_activity_date` исключена из импортируемых полей и шаблона, старая колонка игнорируется. Версия политики входит в план: старый предпросмотр не позволяет применить прежние правила. План различий хранится для проверки и применения, но не выводится построчно: интерфейс показывает только сводные счётчики, подтверждение/отмену и скачивание общего отчёта. `report_workbook` сохраняет исходные строки, добавляет результат, различия, пояснения, ошибки и состояние загрузки; включает фильтры Excel. Истёкший или созданный по старой политике план помечается в отчёте как устаревший без записи в базу. Счётчики в Jinja читаются по ключам (`counts['update']`), чтобы не вывести метод словаря вместо числа.
- Права руководителя и владельца загрузки проверяются сервером, POST-запросы защищены CSRF. Ограничения: 5 МБ XLSX, 32 МБ распакованного содержимого, 5000 строк, 64 колонки. Проверяется формат ИНН, не контрольная сумма и не внешние реестры. Новые тесты используют только временную SQLite.
