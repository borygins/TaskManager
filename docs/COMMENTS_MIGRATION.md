# Переход на единую историю комментариев

Новая версия хранит текст в `comments.body`. В `contact_activities` вместо собственной колонки `comment` используется обязательная уникальная ссылка `comment_id`. Поле `clients.manager_notes` удалено из модели и удаляется из существующей базы скриптом миграции.

**Нельзя запускать новую версию на старой базе без миграции. Приложение должно быть остановлено на всё время обновления, включая проверку результата.** Автоматически при старте эта миграция не выполняется: вместо этого приложение выдаёт инструкцию. Новая пустая база сразу создаётся в новом формате.

## Подготовка и запуск вручную

1. Сохраните предыдущую версию кода для возможного отката.
2. Остановите все процессы приложения и другие программы, изменяющие эту SQLite-базу. Не удаляйте файлы `-wal` и `-shm`: в WAL могут находиться сохранённые изменения.
3. Перед рабочей базой рекомендуется проверить миграцию на её согласованной копии, полученной через существующую функцию бэкапа/SQLite Backup API. Простое копирование одного основного файла работающей WAL-базы для этого не подходит.
4. Из корня проекта запустите:

```powershell
.\.venv\Scripts\python.exe scripts\migrate_comments.py --database .\task_manager.sqlite3
```

Для другой базы передайте её полный путь в кавычках. Не запускайте эту команду одновременно с приложением. Скрипт не читает `.env`, не импортирует приложение, не запускает сервер или планировщик и не создаёт базу, если указанный файл отсутствует. Требуется SQLite версии 3.35 или новее, поставляемый с Python.

Скрипт **сам создаёт обязательную резервную копию через SQLite Backup API** в папке `backups` рядом с базой. Имя содержит `before_comments`, дату и случайный суффикс; прежние файлы не перезаписываются. Можно указать другую папку через `--backup-dir`. Путь к успешно проверенной копии выводится как `Backup saved: ...`. Если копия не создаётся или её проверка не проходит, перенос не начинается.

5. Убедитесь, что команда завершилась с `Migration completed.` и кодом выхода 0. Если база уже была преобразована первой версией скрипта, повторный запуск дополнительно разрешит пустой `funnel_id`, необходимый для автоматического канала `Прочее`, не меняя существующие контакты. После этого дальнейшие запуски выводят `Already migrated. No changes made.` — новые комментарии не добавляются.
6. Только после успешной миграции запустите новую версию приложения. Проверьте несколько карточек, общую историю, последний комментарий в общей выгрузке и журнал контактов. Неподтверждённые импорты нужно загрузить заново.

Автотесты можно запустить отдельно, когда запуск будет разрешён:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -q
```

При подготовке этого изменения миграция, приложение и тесты не запускались по просьбе владельца проекта. Это инструкция для последующей ручной проверки, а не утверждение, что рабочая база уже обновлена.

## Правила переноса

- Существующие комментарии сохраняют ID, текст, автора и время. Для неизвестного источника ставится `legacy`, а не выдуманное «из карточки» или «из Excel».
- Ссылка контакта подбирается по клиенту, автору, точному тексту и времени: старый комментарий должен быть создан от 0 до 5 секунд после записи контакта. Такое окно соответствует прежнему последовательному сохранению. Это эвристика, а не восстановление отсутствовавшего ранее идентификатора связи.
- Связь используется только при единственном совпадении в обе стороны. Один комментарий не может стать текстом двух контактов. При отсутствии или неоднозначности совпадения создаётся отдельный комментарий из текста контакта; прежние комментарии не удаляются. В неоднозначных случаях в истории могут остаться визуальные повторы — это намеренная защита от потери данных.
- Все поля контакта, включая ID, менеджера, дату, результат, реквизиты и текст, проверяются на сохранность. Меняются способ хранения текста и допустимость пустого `funnel_id`: старые ссылки сохраняются, а новые контакты клиента без воронок используют `NULL` и снимок канала `Прочее`. Норма контактов и ранее созданные файлы отчётов не пересчитываются.
- Непустые `manager_notes` переносятся как `legacy_notes`. Если нормализованный по пробелам текст уже есть у того же клиента, новая копия не добавляется. Для новых перенесённых заметок автор остаётся пустым; дата создания означает время переноса. Исходные автор и дата неизвестны, и интерфейс это явно показывает.
- После проверки старые поля удаляются. Обычная выгрузка клиентов теперь берёт последний комментарий из общей истории по времени создания и ID.
- Неисполненные предпросмотры импорта помечаются устаревшими. Выполненные импорты и их исторические отчёты сохраняются.
- `activity_logs` и сохранённые планы импорта остаются историческими снимками действий. Они могут содержать прежний текст, но не являются источником для редактирования комментариев или журналов контактов.

## Безопасность и ошибки

Изменения схемы и данных выполняются в одной транзакции с блокировкой других записей. Внутри перестройки таблиц SQLite проверка внешних ключей временно отключена; перед фиксацией обязательно выполняются `foreign_key_check`, `integrity_check` и проверка соответствия контактов комментариям. Версия фиксируется в `schema_migrations`.

При ошибке изменения базы откатываются. Уже созданная резервная копия сохраняется. При нестандартной/частично изменённой схеме, пользовательских представлениях или триггерах скрипт откажется продолжать, чтобы не потерять дополнительные данные. Не удаляйте найденные объекты ради обхода проверки — сначала разберите причину.

Для отката после успешной миграции остановите приложение, сохраните отдельно текущее состояние базы **вместе с её WAL/SHM, если они есть**, и восстановите проверенную резервную копию под именем основной базы в месте, где нет старых WAL/SHM. Используйте предыдущую версию кода: старый код несовместим с новой структурой. Не смешивайте резервную копию с журнальными файлами от другой версии базы. Изменения, сделанные после миграции, в исходной резервной копии отсутствуют.
